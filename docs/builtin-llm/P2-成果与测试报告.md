## 零、一句话结论 + 三件要先看的事

**「不用自己找大模型 key」这条路跑通了**:全新实例 `docker compose up -d` → 浏览器里选第一张卡
→ 粘一把免费的 `hunt_tools_` key → 三项检测 4.87 秒全过 → 保存热生效 → 真实对话带工具调用
→ 深度分析走 `hunter-deep`。全程不改任何文件、不填第二把 key。

先看这三件事,它们都是实测推翻了原计划的某个假设:

| # | 事 | 影响 |
|---|---|---|
| 1 | **429 让「额度用完」的提示永远到不了用户界面。** 网关按方案返回 429 + 一段写得很清楚的中文引导,而 opencode(AI SDK)把 429 当「等会儿再来」,按 `Retry-After` **无限重试**:实测 17 分钟仍在转圈,用户看到的是一个永不停止的加载,那段中文一个字都没露出来 | 改了 **hermes 网关**:日额度用完返 **402** 而不是 429(`type` 仍是 `insufficient_quota`)。402 在 AI SDK 里不可重试,错误当场交给界面。见第四节 |
| 2 | **`LLM_SCHEMA_SANITIZE` 原来只给了 opencode,api 看不到** | `.env` 写 `=0` 的锁定实例上,opencode 按 0 直连、api 退回数据库里的旧值,设置页显示 1 而实际走 0。compose 的 api 段补上这一项 |
| 3 | **P1 交接的那批 agent 模型变量,坑比记录的更深一层** | 它们在 compose 里是 `${X:-}`,空串会让 `os.getenv(名, 默认值)` 拿不到默认值 —— 这不只影响内置额度,**所有没写 `.env` 的部署**都中招。改成统一走 `runtime_config.agent_model()`:环境变量非空 → 数据库 → 代码默认值 |

## 二、偏离方案的决策,以及为什么

### 决策 A · 日额度用完改返 **402**,不是方案 4.2 写的 429(改的是 hermes)

方案 4.2 与 P1 都写的是「超额返回 OpenAI 兼容错误体」,P1 用了 429。**实测下来 429 这条路是死的**:

```
06:57:08  429 daily_quota_exceeded     ← 用户发了一条消息
06:57:13  429                          ← 客户端重试
06:58:14  429      06:59:15  429
07:00:16  429      07:01:16  429
07:02:17  429      07:03:18  429 …     ← 一分钟一次,一直转圈
```

opencode 用的 AI SDK 把 `408/409/429/5xx` 判为可重试,而 opencode 外面还套了一层重试循环;
把 `Retry-After` 从实测的 33680 秒(9.4 小时)压到 60 秒只是让转圈转得快一点,治不了。
**用户看到的是一个永不停止的加载,那段写清「今天用完了、几点重置、现在能怎么办」的中文一个字都没露出来。**

改成 402 之后:1 秒内出错误卡,`isRetryable: false`,整段中文引导显示在界面上(第五节有截图)。
`type` 仍是 OpenAI 的 `insufficient_quota`,按类型判断的客户端不受影响;
DeepSeek 余额耗尽给的也是 402,hunter-community 的 `lib/modelError.ts` 早就认得这一类。
**限流(60 秒)与并发(5 秒)两种拒绝仍然是 429 + Retry-After** —— 那两种确实是「等会儿再来」。

两个提交:`2e43c3b`(先压 Retry-After,不够)、`c1e42a6`(改 402,治本)。两次都全量跑了 45 条单测。

### 决策 B · `builtin` 只在地址真的是网关时才算数

前端传什么都不能让别的地址顶着内置额度的名义去写 `hunter-chat` / `hunter-deep` 那批模型名。
判据是**路径**不是域名(`…/api/saas/llm/v1`)—— 自建一套 hermes 的人用的是同一套路由,该认。

### 决策 C · 顺手解锁数据供给,而不是「提示用户去填」

任务书写的是「提示『同一把 key 已解锁数据供给』,避免重复填」。**要做到「避免重复填」就得真的替他填**:
那把 key 刚在第 3 步通过了对我们网关的三项检测,网关认的就是 `saas_key.verify()`,
和数据供给是同一套校验。所以保存时直接存,并在第 4 步把结果**显式告诉用户**(不是静默)。
三种情况不动它:环境变量锁定、已经配过、key 不是 `hunt_tools_` 开头。

### 决策 D · agent 模型变量改成「环境变量 → 数据库 → 代码默认值」,而不是只给内置额度打补丁

P1 交接第 1 条只要求「内置额度路径下把这批变量写成 hunter-*」。但查下来这个坑比记录的更广:
compose 把它们写成 `${X:-}`,**没有 `.env` 的部署拿到的是空串**,
`os.getenv("ASSISTANT_MODEL_CHAT", "gemini-3.5-flash")` 返回的是 `""` 而不是默认值 ——
**所有**走向导配置、没写 `.env` 的用户都中招,不只是内置额度。
所以统一成和大模型三件套一样的优先级,顺带把默认值救回来。

调用点全部改成**惰性函数**(`_MODEL = os.getenv(...)` → `def _model(): ...`):
模块级常量在向导热生效之后不会更新,而热生效正是这套东西的卖点。

### 决策 E · `.env.example` 的三项改成留空

原来预填 `LLM_BASE_URL=https://api.openai.com/v1` + `LLM_DEFAULT_MODEL=gpt-4o-mini`。
而 `runtime_config.env_locked()` 的语义是「**任何一项**非空就锁」—— 于是
`cp .env.example .env` 的人反而进不了向导,只看到「这台实例的大模型配置已锁定」。
改成三项留空,并把「留空走向导 / 填了就是锁定」这件事在注释里写清楚。

### 决策 F · 预设卡的 `tool_hit` / `avg_latency_s` 留空

那两个字段的口径是「7 个 golden case」,而本轮没有对 `hunter-chat` 跑那套。
按仓内规矩(`data/llm-presets.json` 的 `note`)「核对不上的字段一律留空」,
改为在 notes 里写向导三项检测的实测耗时,并注明两者口径不同、不可比。

## 四、402 这一节值得单独读

### 现象

网关按方案返回了 429 + 一段很好的中文引导,`curl` 直测完全正确。
但在**对话页上**,用户只看到一个永不停止的转圈,17 分钟后仍在等。

### 排查

| 看哪 | 看到什么 |
|---|---|
| `saas_traffic_log` | `daily_quota_exceeded` 一分钟一条,整整齐齐 8 条还在继续 |
| opencode 日志 | 只有一行 `[hunter-auth] chat.message · verified`,**没有任何报错** |
| 会话消息 | assistant 消息 `parts: []`、`info.error` **是空的** —— 客户端还没放弃,所以还没有"错误"可记 |
| 第一次尝试的修法 | 把 `Retry-After` 从 33680 秒压到 60 秒 → 重试从 5 分钟一次变成 1 分钟一次,**还是无限** |

### 根因

429 在所有 OpenAI 兼容客户端眼里都是「等会儿再来」。
AI SDK 的 `APICallError` 默认 `isRetryable = 408 | 409 | 429 | >=500`,opencode 外面还套了一层。
**日额度用完不是「等会儿再来」,是「今天到此为止」** —— 语义上正是 402 Payment Required。

### 改完之后

```
error: {"name":"APIError","data":{
  "message":"HunterCode 内置模型额度今天用完了（已用 154,686 / 上限 2,000 token）。…",
  "statusCode":402, "isRetryable":false, …}}
耗时 1 秒
```

界面上:标题「今天的内置额度用完了,这次没有生成内容」,正文就是网关那段中文引导本身。

### 前端那一半

`lib/modelError.ts` 原来按状态码套模板,429 会被写成「模型请求太频繁,稍等一会儿再重发」——
方向完全相反。现在:
① 认得出网关的 6 个错误码(`daily_quota_exceeded` / `rate_limited` / `too_many_concurrent` /
`input_too_large` / `hunter_key_required` / `model_not_allowed`),标题说人话、正文用上游原话;
② 认不出 code 但已经拿到一段中文(≥12 字)时同样直接用,**不套模板**;
③ 其余按老规矩(402 余额 / 401 密钥 / 429 限流 / 5xx / 认不出的如实写 + 折叠英文原话)。

`data.responseBody`、`data.message`、`err.message` 三处都找一遍 —— 不同客户端放的位置不一样,
本轮实测到的两种(带 responseBody / 只有 message)在 `scripts/model-error-check.mjs` 里各有一条断言。

## 八、给 P3 的交接

### 8.1 P3 要做什么(方案 5.2 试点期测量计划)

1. **两周只测量不设硬墙**:网关已经在记 `saas_llm_usage`,默认日额度 30 万当保护上限。
2. 两周后出三个分布:**人均日 token**、**输入/输出比**、**深度分析占比**。
3. 用真实分布 × 官方单价算出「每 1000 日活的月成本」。
4. 据此定:默认日额度、`hunter-deep` 要不要单独子额度、要不要分等级。

### 8.2 需要用户拍板的两件事

| # | 要决定的 | 背景数据(实测) | 不决定的后果 |
|---|---|---|---|
| 1 | **额度档位定多少** | P1 实测:一个 opencode 问题 ≈ 54k token;混合单价约 $0.84/1M;30 万/天 ≈ 10 个问题 ≈ $7.6/月/key,1000 日活约 **$7,600/月**。本轮一轮人工回归就吃掉了 307k —— 重度用户一天用满是现实的。2027-01-01 起 flash 涨价,上表要 ×2 | 不定就一直是 30 万,成本随放量线性涨 |
| 2 | **对外开放到什么范围** | 方案 6.2:面向大陆公众提供生成式 AI 服务有备案要求。现在的定位是「只对已申请 `hunt_tools_` key 的自部署用户开放」,不是公开 API | 不定就只能继续小范围灰度,写不进对外宣传 |

另外两件可以由我们自己决定、但建议用户知道的:
- `hunter-deep` 的子额度(遗留问题 1);
- 要不要把「7 个 golden case」对 `hunter-chat` 跑一遍,好让预设卡上有命中率(遗留问题 2)。

### 8.3 P3 动手前要知道的

- **网关已经生产可用**,P3 不需要改 hermes 的功能,只加报表查询。
- 记账口径在 `llm_quota.py`:输入 = `prompt_tokens`,输出 = `total_tokens − prompt_tokens`(**含 thinking**),
  `estimated=true` 的行是原生渠道降级时估的,报表里要分开算。
- 测试 key 是 `saas_key` id=42(`llmgw-p1-test`),**本轮把它的 `quota_daily` 改小过又改回 NULL**,
  Redis 日计数器 `llmq:42:20260919` 清过一次(为了出干净的截图)—— 它的当日用量数字不可用于统计。
- 测试服务器 `~/hunter-p2` 那套实例可以直接接着用。
