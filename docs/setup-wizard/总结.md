> 把偏离设计的决策和遗留待办摊开。**

## 零、目标达成情况

| 指标 | 开工前 | 现在 |
|---|---|---|
| 从零到第一次对话需要编辑的文件 | `.env` 至少 4 处 | **0 个** —— `git clone` → `docker compose up -d` → 浏览器里走完五步向导 |
| 云平台部署 | 不支持（compose 里 13 处挂仓库文件、迁移只在建卷时跑、`JWT_SECRET` 缺了拒绝启动） | **五个平台的模板 / 清单 / compose 都就绪**，但**都没上架** |
| 配置错误暴露时机 | 发第一条消息后，表现为空回复 | 向导第 3 步当场检测、分类报错，**测不通不让保存** |
| 升级后数据库 | 缺表缺列需手工补 | api 启动自动迁移（实测把一个真实的 500 故障修好了） |
| 换大模型 | 改 `.env` + 重启容器 | 向导里改，**热生效不重启**（实测 283 ms ～ 17.6 s） |

**一句话**：原来的形态上不了任何云平台，也要求用户先会改配置文件；现在两头都解决了。
**没做到的那件事**：五个平台一次真实部署都没做过、一家都没上架 —— 因为我们没有
任何一个平台的账号。所以 README 里**没有部署按钮**，只有文档。

## 三、偏离设计方案的决策（及原因）

| # | 设计方案原本怎么写 | 实际怎么做 | 为什么 |
|---|---|---|---|
| 1 | 热生效走 `PATCH /config` | **`PATCH /global/config`** | R0 实测：`PATCH /config` 写的那个文件没人读 |
| 2 | SKILL 同步写 huntercode 插件 `hunter-skill-sync.ts`，发新基础镜像标签 | **不写插件、不发新标签**，用 opencode 原生 `skills.urls` | R0 实测原生能力已完整覆盖（0.07 秒可见、模型真能调用）。少一个 fork 改动就少一处漂移。**省了 1～2 天** |
| 3 | 迁移文件「全部可重复执行」 | **不成立**，`0010` 与 `0014` 定义同一个视图且 0014 多一列 | `CREATE OR REPLACE VIEW` 不许减列。已在 0010 开头补 `DROP VIEW IF EXISTS` 根治 |
| 4 | 迁移由 postgres 的 initdb 执行 | **必须排在 api 的 `init_db()` 之后** | 7 个迁移 ALTER 的目标表是 `init_db()` 建的，原来那 7 个一直在静默失败 |
| 5 | 云平台上用共享卷传密钥 | **改成模板生成 + 环境变量注入** | Zeabur 官方明说不支持共享卷。但 Coolify / Dokploy / 1Panel 是单机 Docker，那里**仍然用共享卷**（少两个能填错的地方） |
| 6 | Zeabur 的 `${PASSWORD}` 一个模板一把 | **每个服务一把** | 官方文档原文 "A random password generated by Zeabur **for each service**"。要四把不同的密钥只能借位到四个服务再 `expose` |
| 7 | 1Panel 表单用 `type: random` | **`type: password` + `random: true`** | 官方规范里没有 `type: random` |
| 8 | Railway 写「模板文件」 | **没有模板文件** —— 官方流程是先跑通项目再反向生成模板 | 官方文档如此。所以交付的是「要在控制台里敲什么」的逐条清单 |
| 9 | 第二批做 Railway + 1Panel | **1Panel 在 M3 提前做完**；M4 把 Coolify / Dokploy（原第三批）提上来 | 这两家直接吃 compose，改造成本极低，顺手就做了 |
| 10 | 没有账号就无法验证 | **等价验证**：把模板机械翻译成 compose，用平台自己的方式生成密钥，本机从空卷跑 | 这是整个项目最关键的一个方法决策。五个平台全靠它，挖出来的真问题里有 6 个只有这样才能发现 |
| 11 | README 加各平台部署按钮 | **一个按钮都不加** | 设计方案 5.6 自己写的前提是「上架并实测通过后才加」。一条都没满足 |

## 四、这个项目里最值得记住的几件事

1. **「空的比假的好」在系统里也成立。** 未配置大模型时 llm-shim 立刻返回中文错误，
   而不是让请求挂住（实测挂 100 秒以上）；没有行情 key 时模型如实说
   「暂未配置，无法获取实时行情」，**不编一个价格**。这两条都是实测反复确认过的。
2. **最难查的失败是「全绿但不工作」。** 本项目遇到过三次：
   api 缺 `LLM_SHIM_URL`（向导五步全绿、`engine-ready` 也 true，发消息永远没回复，
   日志一条报错都没有）；api 绑 `::` 之后只收 IPv6（自己的日志一切正常，别人全连不上）；
   opencode 等 api 只等 3 秒（重新部署后配置静默失效）。
   **这三个都只能靠端到端真跑出来。**
3. **本机的 Docker 语义是最宽松的，拿它当基准一定会漏。** 具名卷会把镜像内容拷进空卷、
   没有 `lost+found`、`depends_on` 还能编排启动顺序 —— 这三条云平台上一条都不成立。
   等价验证工具后来**刻意模拟**了这些差异，才把两个必炸的配置炸出来。
4. **发布前跑一遍完整的用户路径，比多写一个功能值钱。** M4 的九个问题里有五个是
   回归挖出来的，其中两个（合规弹窗盖住向导、第 4 步文案承诺做不到的事）影响的是
   **每一个新用户看到的第一屏**。
5. **文档里的每个数字都要能指回一条命令。** 这也是为什么每份报告都带「命令 / 结果 /
   实测数据」三列，以及为什么「未测」要写出来 —— 写「未测」比写一个好看的估算值有用。

## 六、这套东西怎么继续维护

- **加一个新平台**：在 `deploy/tools/template-to-compose.py` 里加一个
  `translate_<平台>`，其余测试脚手架一行都不用改；先问清楚「这个平台的卷是什么语义」。
- **每抓到一个真问题，就往 `deploy/tools/validate-templates.py` 里加一条规则。**
  它从 24 项长到 58 项，新增的每一条都对应一次真实的踩坑。
- **改了运行时代码就要跑四条路径**（老用户升级 / 本地全新 / 云平台模式 / 开发模式），
  M4 报告第四节有完整的命令与判据。
- **发版前**：`validate-templates.py` 全绿 → 四条路径全过 → 演示站回归 →
  `m4tests/check-manifests.sh <标签>` 确认四个镜像都是 amd64 + arm64。
