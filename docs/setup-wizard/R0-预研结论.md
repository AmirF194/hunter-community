## 一、`PATCH /config` 热生效（设计方案 3.3、第十节 1、2）

### 1.1 结论：`PATCH /config` 不可用

`PATCH /config` 返回 200、耗时 **9 ms**，确实写出了文件，但**写的文件永远不会被读回来**：

```
PATCH /config -> 200 耗时 0.009 秒
返回体: {"model": "hunter-llm/gemini-3.5-flash", ...}      ← 回显的是入参
GET /config（紧接着）-> model = hunter-llm/gemini-3.8-flash  ← 仍是旧值
models = ['gemini-3.8-flash']                                ← 新模型压根没进来
```

容器内确认文件写成功了，但没人读它：

```
/opt/opencode-workspace/config.json   ← PATCH 写的，model=hunter-llm/gemini-3.5-flash
/opt/opencode-workspace/opencode.json ← gen-config 写的，model=hunter-llm/gemini-3.8-flash（生效的是这份）
```

PATCH 之后新建会话发消息，`modelID` 仍然是 `gemini-3.8-flash`。

**源码依据**（huntercode dev `346f111`）：

- `packages/opencode/src/config/config.ts:624` `Config.update` 写的是 `path.join(InstanceState.directory, "config.json")`，实例目录就是容器工作区 `/opt/opencode-workspace`。
- 实例配置加载（同文件 `loadInstanceState`）只读这四类来源，**没有工作区根的 `config.json`**：
  1. 全局目录 `~/.config/opencode/` 下的 `config.json` / `opencode.json` / `opencode.jsonc`（第 258–260 行）
  2. `OPENCODE_CONFIG` 指定的文件
  3. `ConfigPaths.files("opencode", ctx.directory, ctx.worktree)` —— 从实例目录**向上**找 `opencode.jsonc` / `opencode.json`（第 405 行）
  4. `.opencode` 目录与 `OPENCODE_CONFIG_DIR` 下的 `opencode.json` / `opencode.jsonc`（第 424–433 行）

也就是说，设计方案第一节第 9 行「`PATCH /config` 写实例目录 `config.json`，下次请求重建实例、重读配置」只对了前半句：**实例确实被销毁重建了，但重建时读不到那份 `config.json`**。

> 设计方案第十节第 2 项问「两者内容不一致时谁生效」——答案是 `opencode.json` 生效，`config.json` 不参与合并，两者冲突这件事本身不存在。

### 1.2 结论：`PATCH /global/config` 可用，且很快

`PATCH /global/config` 走的是 `Config.updateGlobal`：写 `~/.config/opencode/opencode.jsonc`（首选候选文件），**调用 `invalidate()` 清掉全局配置的常驻缓存**，并在内容有变化时 `disposeAllInstancesAndEmitGlobalDisposed` 销毁全部实例（`handlers/global.ts`）。两件事都做了，所以配置能真正重新加载。

A↔B 来回各切一次的实测（同一网关换模型名）：

| 指标 | 切到 `gemini-3.8-flash` | 切到 `gemini-3.5-flash` |
|---|---|---|
| `PATCH /global/config` 返回 | 34 ms | 48 ms |
| `GET /config` 反映新模型 | PATCH 后 0.53 s | PATCH 后 0.52 s |
| `GET /mcp`（含实例重建 + MCP 全部重连） | 3.60 s · **6/6 connected** | 3.44 s · **6/6 connected** |
| 新会话首个请求（带真实上游） | 3.69 s · modelID=`gemini-3.8-flash` | 3.42 s · modelID=`gemini-3.5-flash` |
| **PATCH → 新对话返回 总计** | **7.87 s** | **7.42 s** |

判定线是「30 秒内新对话使用新模型、MCP 全部重新连接」——**通过，余量很大**。

其他实测：

- **旧会话可读**：切换前创建的 2 个会话 `GET /session/{id}/message` 均 200，消息数不变；会话总数从 4 → 9 只增不减。
- **旧会话可续聊**：切换后往切换前的会话再发一条，200、1.32 s、用新模型。
- **换 baseURL 确实生效**：把 `options.baseURL` 改成 `http://127.0.0.1:59999/v1`，`GET /config` 立刻回显新地址，证明换的不只是模型名。

### 1.3 生效的前提：项目级 `opencode.json` 会覆盖全局配置

第一次 `PATCH /global/config` 时出现了「一半生效」：

```
GET /config → model = hunter-llm/gemini-3.8-flash          ← 没变（项目文件里的值）
              models = ['gemini-3.5-flash','gemini-3.8-flash']  ← 变了（全局的 provider 合并进来了）
```

原因就是 1.1 列的合并顺序：全局配置先合并，**项目级 `opencode.json`（gen-config 写的那份）后合并、优先级更高**，于是它里面的 `model` 把全局的盖掉了。

把容器内 `/opt/opencode-workspace/opencode.json` 的 `provider` / `model` 两个键剥掉、`POST /instance/dispose` 之后：

```
GET /config → model = hunter-llm/gemini-3.5-flash   ← 全局配置生效
GET /mcp    → 6/6 connected（2.45 s）
新会话对话  → modelID=gemini-3.5-flash，并成功调用 watchlist_stock_quickview 拿到真实行情
```

**→ M1 必须做的改动**：`gen-config.py` 分两处写。

| 内容 | 写到哪 | 理由 |
|---|---|---|
| `mcp`、`instructions` | 项目 `/opt/opencode-workspace/opencode.json`（不变） | 与大模型配置无关，不需要热改 |
| `provider` / `model`（配置来自**数据库**时） | 全局 `~/.config/opencode/opencode.jsonc` | 只有这里才能被 `PATCH /global/config` 热改 |
| `provider` / `model`（配置来自**环境变量**时） | 项目 `opencode.json`（保持现状） | 项目文件优先级天然最高，正好实现「环境变量锁定」；向导即使误调也改不动 |

### 1.4 备选方案实测

| 接口 | 耗时 | 效果 |
|---|---|---|
| `POST /global/dispose` | 374 ms | 销毁全部实例。之后 `GET /mcp` 2.58 s、6/6 重连，新对话 3.42 s。**但它不清全局配置缓存**（缓存只由 `updateGlobal` 里的 `invalidate()` 清），所以单用它改不了配置，只能当「实例卡住时的重置手段」 |
| `POST /instance/dispose` | 10 ms | 销毁当前实例，之后 `GET /mcp` 3.53 s、6/6 重连。同样不清全局缓存 |

**采用结论：热生效用 `PATCH /global/config`**，不需要设计方案 3.3 里的「入口脚本子进程重启」降级方案，M2 不用加那一天。

### 1.5 两个必须记下的副作用

1. **`models` 会累积**。`updateGlobal` 是 `mergeDeep`，删不掉键。两次切换后全局配置文件里同时留着 `gemini-3.5-flash` 和 `gemini-3.8-flash`。属外观问题——`model` 指向新模型、对话用的也是新模型；容器重启时 `gen-config` 整份重写即清空。向导第 5 步的就绪判定用「当前 `model` 等于新模型」而不是「models 列表只有一个」。
2. **上游不可达时对话是「挂住」而不是「报错」**。把 baseURL 指向不可达地址后，一条 `你好` 超过 100 秒没有返回。**所以 llm-shim 的「大模型尚未配置」必须由 shim 自己立刻返回 OpenAI 兼容错误体**，绝不能指望上游超时——否则用户在向导前发的第一条消息会转圈几分钟。

安全观察（不是新增风险，但要写进文档）：`GET /config` 明文回显 `apiKey`，全局配置文件里也是明文（容器可写层，recreate 即消失）。向导前端**不要**直接代理 opencode 的 `/config`。

## 二、SKILL 同步（设计方案 3.5、第十节 3）

### 2.1 结论：不写 huntercode 插件，用 opencode 原生 `skills.urls`

查 huntercode 插件钩子（`packages/plugin/src/index.ts` 的 `Hooks` 接口）：`dispose`/`event`/`config`/`tool`/`auth`/`provider`/`chat.*`/`tool.execute.*`/`experimental.*`/`permission.ask`/`command.execute.before`/`shell.env`/`tool.definition`。**没有任何扩展 HTTP 路由的能力**，插件无法暴露一个能被 api 调用的「重新同步」入口。插件工厂函数本身在实例初始化时执行、可以做异步 IO，所以「实例初始化时同步」是能做的——但没必要做了，因为原生能力更强。

`packages/opencode/src/skill/index.ts:239` 起：

```ts
for (const url of cfg.skills?.urls ?? []) {
  const pulledDirs = yield* discovery.pull(url)
  for (const dir of pulledDirs) yield* scan(state, dir, SKILL_PATTERN)
}
```

`Discovery.pull(base)`（`skill/discovery.ts`）：
- 拉 `<base>index.json`，schema 为 `{"skills":[{"name": str, "files": [str], "version": str?}]}`
- 每个文件从 `<base><name>/<file>` 下载到 `~/.cache/opencode/skills/<name>/<file>`
- 带 `version` 时做 **staging 目录 + 原子 rename** 换版；`version` 不变则只补缺失文件
- 缺 `SKILL.md` 的条目会被跳过并打 warning

`POST /skill/refresh`（`Skill.refresh`）会 `invalidate(discovered)` + `invalidate(state)`，**下一次读取时整套发现流程重跑，包含 URL 拉取**——所以 api 写完 SKILL 后调一次 `/skill/refresh` 就够了（api 现在已经在调）。

### 2.2 实测

预发栈内起了一个静态文件服务 `r0skills`（compose 网络内），用 `PATCH /global/config` 注入 `skills: {urls: ["http://r0skills:8080/"]}`：

| 步骤 | 耗时 | 结果 |
|---|---|---|
| PATCH 注入 urls | 13 ms | — |
| 紧接着 `GET /skill` | 0.46 s | 8 个，含新的 `r0-demo`，location = `/home/hunter/.cache/opencode/skills/r0-demo/SKILL.md` |
| **注入 → 可见 总计** | **0.48 s** | — |
| 模型实际使用 | 7.36 s | 调用了 `skill` 工具，答出 SKILL 里埋的口令 `ALPHA-111` ✅ |

改内容（`ALPHA-111`→`BETA-222`）+ 新增第二个 SKILL + `version` 从 `1` 改 `2`：

| 步骤 | 耗时 | 结果 |
|---|---|---|
| 不刷新时 `GET /skill` | — | 8 个（旧缓存，符合预期） |
| `POST /skill/refresh` | 0.05 s | 返回 skill 数 = 9 |
| 之后 `GET /skill` | 0.02 s | 9 个，`r0-demo` + 新增 `r0-second` 都在 |
| **写入 → 可见 总计** | **0.07 s** | — |
| 模型实际使用 | — | 两个口令都答对：`BETA-222`、`GAMMA-333` ✅ |

**本地开发路径也免重启**：往挂载的 `~/.config/opencode/skills/` 直接写一个 `r0-local/SKILL.md`，`POST /skill/refresh` 0.02 s 后 `GET /skill` 可见（location 就是该目录）。即 3.5 里「本地若挂了目录，同时写目录保持向后兼容」这条成立且同样实时。

判定线是「api 装 SKILL 后模型 60 秒内可见」——**通过，实测 0.07 秒**。

### 2.3 推荐做法（M1 落地）

1. api 新增 `GET /api/internal/skills/{key}/index.json` 与 `GET /api/internal/skills/{key}/{name}/{file}`。
   - **鉴权只能放 URL 路径段**：`Discovery.pull` 用裸 `GET` + `acceptJson`，不带任何自定义头，没法传 `X-Hunter-Internal-Key`。把 `HUNTER_INTERNAL_KEY` 作为路径段，配合「shim/opencode 不对外暴露端口」即可。
   - `version` 用「该 SKILL 全部文件内容的 sha256」，内容不变就不触发重下。
2. `gen-config.py` 往全局配置里写 `skills: {urls: ["http://api:8000/api/internal/skills/<key>/"]}`。
3. api 写完用户 SKILL 后照旧调 `POST /skill/refresh`（已有代码），无需新增 dispose 调用。
4. **huntercode 不需要任何改动**，因此 M1 不需要发 `hc-v1.18.12-slim.2` 基础镜像标签，opencode 包装镜像继续 `FROM ghcr.io/agentpit-io/hunter-opencode:1.18.12-slim.1`。

## 三、内存峰值（设计方案第十节 4）

`docker stats` 每 2 秒采样（实际约 4 秒/轮，6 个容器串行取数），共 415 条样本、72 个时间点，覆盖空闲基线与三段负载。单位 MB。

| 服务 | 空闲 60 s | 全市场扫描 | 深度分析 | **两者并发** |
|---|---|---|---|---|
| opencode | 869.1 | 881.2 | 856.7 | 869.8 |
| web | 139.0 | 138.7 | 138.7 | 138.7 |
| api | 104.7 | 171.9 | 189.7 | **203.5** |
| postgres | 33.4 | 33.4 | 34.8 | 33.7 |
| llm-shim | 15.5 | 15.6 | 15.5 | 15.6 |
| redis | 9.7 | 9.6 | 9.9 | 9.8 |
| **合计** | **1171.4** | **1250.5** | **1245.3** | **1271.1** |

全程（含热切换与 SKILL 测试）各服务峰值之和 **1284.3 MB**。

负载的真实性佐证：
- 深度分析走的是 `POST /api/online-analysis/start` + SSE 流，耗时 **57.6 s**，落库报告 id 430「贵州茅台 / BUY / confidence 0.75 / duration_ms 56799」。
- 全市场扫描经 opencode 对话触发 `screener_market_screen` MCP：扫描 A 股 5237 只、命中 312 只、返回前 20，端到端 **16.4 s**。

**结论**：
- 唯一的内存大头是 opencode（占 68%），而且**几乎与负载无关**——它是常驻占用，不是峰值风险。真正随负载涨的是 api（+99 MB）。
- 设计方案 5.3 的「最低 2 核 2 GB、推荐 2 核 4 GB」**成立**，不需要调整。2 GB 机器留给系统约 700 MB，紧但可跑；4 GB 舒适。
- 镜像体积（本机 `docker images`）：web 1.67 GB、api 909 MB、opencode 618 MB、postgres 420 MB、python:3.12-alpine 83.5 MB、redis 61.2 MB，合计约 3.8 GB → 磁盘建议 ≥ 10 GB 成立。

## 四、卷首次挂载属主（设计方案第十节 6）

opencode 镜像 `USER=hunter`(uid 1001)、`WorkingDir=/opt/opencode-workspace`。

| 场景 | 卷根属主 | `mkdir /home/hunter/.local/state` | 结论 |
|---|---|---|---|
| **Docker 具名卷**（新建空卷挂 `/home/hunter/.local`） | `1001:1001` | ✅ OK，写文件也 OK | 可用 |
| 镜像内（不挂卷） | `hunter:hunter`，目录**已存在** | — | 是上一行成立的原因 |
| **模拟 K8s PVC**（空目录 bind mount，属主 `1000:1003`） | `1000:1003` | ❌ `Permission denied` | 不可用 |
| **模拟 K8s PVC**（属主 `0:0`） | `0:0` | ❌ `Permission denied` | 不可用 |

关键差别：**Docker 具名卷首次挂载时会把镜像里该路径的内容与属主拷进卷**，而 K8s PVC / bind mount 不会。镜像里 `/home/hunter/.local` 现在是存在的（属主 1001），所以 Docker 路线天然可写。

> 顺带更正 `docker-compose.yml` 里那段老注释：「镜像里根本没有 /home/hunter/.local」——在 `1.18.12-slim.1` 上已经不成立了，该目录存在且属主正确。原来那个 `EACCES: mkdir '/home/hunter/.local/state'` 的坑在这个镜像上复现不了。挂 `.local` 整个目录的做法仍然保留（它同时解决了 `state` 与 `share` 两处）。

**对模板的要求**：
- Zeabur / Railway / 1Panel / Coolify / Dokploy（compose 或 Docker 卷语义）：**无需额外处理**。
- Sealos 等 K8s 平台：模板必须给 opencode 的 Pod 设 `securityContext.fsGroup: 1001`，或加一个 `initContainer` 以 root `chown -R 1001:1001`。
- opencode 入口脚本增加一步可写自检：`/home/hunter/.local` 不可写时打印明确中文报错（「会话数据目录不可写，云平台需要把卷属主设为 uid 1001，见 docs/deploy/…」）并退出，而不是等插件 mkdir 失败后重启循环。**列入 M1 范围**。

## 六、顺带核实到的、会影响 M1 的事实

1. **GHCR `latest` 就是 main**：api/web 两个 `latest` 镜像的 `org.opencontainers.image.revision` 都等于 main 的 `404dda86…`。预发栈因此可以直接用预构建镜像，不必在 agentpit 上跑 web 的 Next.js 构建。
2. **`/opt/opencode-workspace` 不是挂载点**，`gen-config.py` 生成的 `opencode.json` 落在容器可写层，重建容器即消失、启动时重新生成——这正是设计方案 3.3 说的「不依赖顺序」能成立的基础。
3. **`~/.config/opencode` 只有 `skills` 子目录被挂载**（当前 compose 把 `./user-skills` 挂到 `~/.config/opencode/skills`），父目录在可写层，所以 `PATCH /global/config` 写的 `opencode.jsonc` 也是「重建即消失」，与第 2 点一致。
4. opencode 每次实例重建都会重新加载全部 6 个插件（日志里 `[hunter-mcp-context] loaded` 等 6 行会重复出现），这是判断「热生效是否真的发生」的一个可靠日志信号。

## 七、对 M1 / M2 的结论落地

| 设计方案条目 | 原方案 | 按实测改为 |
|---|---|---|
| 3.3 热生效 | `PATCH /config` | **`PATCH /global/config`**；`opencode_admin.apply_llm()` 按此实现 |
| 3.3 gen-config | 一份 `opencode.json` 全写 | **分两处**：mcp/instructions → 项目 `opencode.json`；provider/model 在「来自数据库」时写全局 `~/.config/opencode/opencode.jsonc`，在「来自环境变量」时仍写项目文件（天然锁定） |
| 3.3 降级方案 | 需要入口脚本子进程重启 | **不需要**，`PATCH /global/config` 已满足判定线（7.4～7.9 s ≪ 30 s） |
| 3.3 llm-shim | 未配置时返回中文错误 | 不变，但**必须 shim 自己立刻返回**——实测上游不可达会挂住 >100 s |
| 3.5 SKILL 同步 | huntercode 新增 `hunter-skill-sync.ts` 插件 | **不写插件**。用原生 `skills.urls` + `POST /skill/refresh`；鉴权走 URL 路径段。**M1 不需要发 `hc-v1.18.12-slim.2`** |
| 3.1 opencode 包装镜像 | `FROM hunter-opencode:<新标签>` | 继续 `FROM ghcr.io/agentpit-io/hunter-opencode:1.18.12-slim.1` |
| 3.1 入口脚本 | — | **新增**：`/home/hunter/.local` 可写自检 + 中文报错（K8s 平台需要） |
| 5.3 资源建议 | 最低 2 核 2 GB / 推荐 4 GB | 不变，实测支持（峰值 1271 MB） |
| 第十节 6 卷属主 | 「各平台新卷可写」 | Docker 语义平台 ✅；**K8s 平台必须 `fsGroup: 1001`**，写进 Sealos 模板与 `docs/deploy/` |
| 第十节 5 GHCR | Sealos 实测 | agentpit / fin-r1 ✅；**国内平台未测**，留 M3 |
| 3.1 多架构 | api/web/opencode/llm-shim | api、web 当前只有 amd64，**M1 必须补 arm64** |

M2 因为不需要降级方案、也不需要写 huntercode 插件，**预计比原排期省 1～2 天**。
