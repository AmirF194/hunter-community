## 零、一句话

`git clone` → `docker compose up -d` → **浏览器里五步配完大模型就能对话**，
全程不改任何文件；第 3 步当场做连通 / 对话 / 工具调用三项检测，**测不通不让保存**；
最后一步**不重启任何容器**热生效。

## 二、偏离设计方案的决策与原因

| # | 方案原写法 | 实际做法 | 原因 |
|---|---|---|---|
| 1 | 「公网访问且配置了口令 → 必须输入口令」（言下之意本机访问即使配了口令也跳过） | **配了口令就一律要**，不管来源看起来是不是本机 | 安全性从「来源判断正确」变成「有没有口令」。后者伪造不了，前者在裸 compose 下伪造得了（见第三节 3.1）。云平台模板必设口令 ⇒ 公网实例必然要口令。代价只是本机用户自己设了口令也要敲一次，那是他自己的选择 |
| 2 | `/api/setup/status` 里汇总「服务、迁移、密钥……」 | **拆出 `GET /api/setup/env-check`** | `/status` 在**对话页每次加载**都会调（判断要不要跳向导），不能带着一串 3 秒超时的 socket / HTTP 探测。拆开之后 `/status` 是纯读库 |
| 3 | 第 5 步调 opencode `PATCH /config` | `PATCH /global/config` | R0 实测结论，M1 已改，这里只是照用 |
| 4 | 第 3 步失败分类里没有「余额不足」「限流」 | 补了 402 / 429 两类 | 实测最常见的两种，且用户的下一步动作完全不同 |
| 5 | — | 新增 `POST /setup/reopen` | 4.1 要求设置页有「重新运行初始化向导」，但清完成标记需要一个接口 |
| 6 | — | 第 4 步平台 key 在多用户、未建账号时会 401 | 复用的 `/api/hunter/unlock` 要求登录。文案改成「先跳过，最后一步建完管理员再来填」，不为此另开一条免登录写接口（那是仓内铁律里的坑） |

## 三、方案之外、实测才发现的问题（都已修）

### 3.1 来源判断可以被伪造 —— 在**演示站**上实测复现

给演示站 `GET /api/setup/status` 加一个头：

```bash
curl -H 'X-Forwarded-For: 127.0.0.1' https://hunter-community.agentpit.io/api/setup/status
```

修之前返回 `authed: true`、`source.kind: "local"`，`GET /api/setup/env-check` 也拿得到
（服务拓扑、迁移状态、密钥长度）。根因是两处写法凑在一起：

* nginx 的 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for` 是**追加**写 ——
  客户端自己带的值**原样留在最左边**，nginx 看到的真实地址追加在末尾；
* 而 `setup_guard` 取的是**最左边**那一项。

修法两处：

1. web BFF **优先转发 `X-Real-IP`**（nginx 对它是 `proxy_set_header ... $remote_addr`，**覆盖**写，客户端带的会被丢掉）；
2. `setup_guard` 从 `X-Forwarded-For` 取**最右边**那一项（离我们最近的那一跳亲手写的）。

修复后在演示站上四种伪造全部被拒：

| 伪造 | 修前 | 修后 |
|---|---|---|
| `X-Forwarded-For: 127.0.0.1` | `authed: true` · env-check **200** | `authed: false` · env-check **401** |
| `X-Real-IP: 127.0.0.1` | — | `authed: false` |
| 两个头一起 | — | `authed: false` |
| 不伪造（真公网来源） | `authed: false` | `authed: false` |

> **仍然要知道的边界**：裸 `docker compose`（前面没有任何反代）时，Next.js 对
> `x-forwarded-for` 是 `??=`，客户端自己带了就不会被覆盖，协议层分不出「Next 补的」
> 和「客户端塞的」。**这一条只能靠 `HUNTER_SETUP_TOKEN` 解决**，README、
> `.env.example`、向导第 1 步的黄色警告三处都写明了。

### 3.2 向导说配好了，第一条消息却回「大模型尚未配置」

预发栈上走完向导，回到对话页发第一条消息，得到的是 llm-shim 的「大模型尚未配置」，
页面底部标着 `hunter-unconfigured`——**而 opencode 的全局配置里明明是新模型**。

根因是 M1 交接第 3 条那件事的另一面：热生效走 `updateGlobal`，它是 **mergeDeep**，
占位模型名会一直累积在 provider 的 `models` 里。于是：

```
GET /config           → model: "hunter-llm/gemini-3.8-flash"     ← 对的
GET /config/providers → default: {"hunter-llm": "hunter-unconfigured"}   ← 前端读的是这个
                        models:  ["hunter-unconfigured", "gemini-3.8-flash"]
```

前端 `resolveModelKey` 判「还在清单里就算有效」，于是继续拿占位名发消息。

修了三处（`apps/web/app/chat/lib/opencodeClient.ts`）：
* 新增 `currentModelKey()` 读 `GET /config` 的 `model` —— 那才是「这台实例选定的那个」；
* `defaultModelKey` / `resolveModelKey` 都先问它，占位名一律不认；
* `listProviders` 把占位名从模型选择器里过滤掉（选中它只会得到一句「未配置」）。

外加向导第 5 步就绪之后**主动**把新模型写进 `localStorage.hunter_chat_model`
（用户刚挑的就是它）。两边一起修：主动写是正路，占位名不认是兜底。

### 3.3 模型名写错被报成「key 无效」

演示站那台 OneAPI 网关对写错的模型名回的是 **HTTP 403** +「该令牌无权使用模型：xxx」。
先按状态码判就会显示「key 无效或没有权限」—— 用户会拿着一把好 key 去重新申请，
而真正要改的是模型名。

现在**先看报错里提没提模型**（逐字出现模型名，或命中中英文的模型类关键词），
提了就按模型名报，并列出这个地址上可用的模型。实测：

```
模型名不对，或这把 key 没有这个模型的权限（HTTP 403）：该令牌无权使用模型：gemini-9.9-nonexistent
；这个地址可用的模型里有：gemini-embedding-001、gemini-3-pro-preview、…
```

### 3.4 全新安装校验不了平台 key

第 4 步粘一把平台 key，返回的是「连不上 Hunter 服务器（Request URL is missing an
'http://' or 'https://' protocol）。检查网络后重试。」——**原因说反了**，网络没问题。

根因：M1 3.7 把 compose 里 `HUNTER_UPSTREAM_URL` 的兜底改成空，
`hunter_key.manifest()` 拼出来的 URL 因此没有协议头。

现在：
* **没有 key 就一个请求都不发** —— 独立运行模式下不该因为打开一个页面就去连官方；
* 用户**主动粘**一把 `hunt_tools_` key 时，没配上游就问官方平台（那把 key 本来就只能从那里申请）。

为什么这里可以回落到官方、而 `LLM_BASE_URL` 不行（M1 3.4）：后者是「用户没配就把他的**对话内容**
发给我们，他并不知情」；这里是「用户主动交了一把只有我们能验的 key，问一句它有效吗」。
**数据请求那条路（`providers/data_source/hunter_tools.py` 读 `UPSTREAM`）一个字没动**，
独立模式下仍然不指回官方。

### 3.5 页面上出现了 markdown 的星号

`**真探测**` 这类写法在纯文本渲染里原样显示成星号。4 处改成 `<strong>`，
后端两处直接去掉强调。

### 3.6 `page.tsx` 不许导出约定之外的字段

向导的共用小组件原来放在 `app/setup/page.tsx` 里 export，`next build` 直接失败：

```
Type error: Page "app/setup/page.tsx" does not match the required types of a Next.js Page.
  "td" is not a valid Page export field.
```

拆到 `app/setup/lib/ui.tsx`。

### 3.7 「大模型尚未配置」的文案在说一件已经不成立的事

llm-shim 与 gen-config 里写着「或等初始化向导上线后在首页完成配置」——
M1 时期这么写是对的（那时候确实没有），现在向导上线了，改成指向 `/setup`。

## 六、遗留问题

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | **裸 compose（无反代）时来源判断仍可伪造** | 暴露在公网且没设 `HUNTER_SETUP_TOKEN` 的实例，任何人都能进向导 | 协议层无解，只能靠口令。README / `.env.example` / 向导第 1 步三处告警；**云平台模板必须生成随机口令**（M3） |
| 2 | 演示站自己没有设 `HUNTER_SETUP_TOKEN` | 它是锁定 + 多用户实例，向导改不了任何东西；但 `env-check` 会暴露服务拓扑与密钥长度（有反代，当前伪造不进来） | 建议给演示站 `.env` 加一行 `HUNTER_SETUP_TOKEN`，本轮**没有动它**（不擅自改别人在用的实例配置） |
| 3 | 占位模型名 `hunter-unconfigured` 仍留在 opencode 的 provider 清单里 | 只影响清单，不影响使用（前端三处都不认它了）；容器重启后 `gen-config` 整份重写才真正清掉 | 要根治得让 `updateGlobal` 支持删键，或 apply 之后触发一次配置重写。M3 评估 |
| 4 | 锁定计数是**进程内**状态 | `docker compose restart api` 会清掉「锁 15 分钟」 | 能重启容器的人本来就有主机权限，不在威胁模型内；**改多 worker 时必须一起换成 Redis**，否则限流和锁定会按 worker 各算一份（代码注释已写明） |
| 5 | 第 4 步平台 key 在「多用户 + 还没建账号」时会 401 | 云平台首次部署的用户要在第 5 步建完管理员之后再回来填 | 文案已说明；要彻底解决得让 `/api/hunter/unlock` 认初始化会话，但那是给一个免登录写接口开口子，没做 |
| 6 | arm64 运行时仍未测（M1 遗留 #1 的后半） | 只验证了 CI 能产出 arm64 产物 | M3 上云平台时用真实 arm64 实例验 |
| 7 | 国内平台拉 GHCR 未测（M1 遗留 #2） | Sealos / 1Panel 可能受阻 | M3 |
| 8 | `apps/api/tests/` 的既有测试仍不是可用的 pytest 套件（M1 遗留 #6） | CI 只能点名跑文件 | 单独立任务 |

## 八、给 M3 的交接

1. **云平台模板必须为 `HUNTER_SETUP_TOKEN` 生成随机值**，并在部署完成页 / 变量面板里展示。
   这是遗留问题 #1 的唯一解法，不是可选项。
2. **模板要把 `HUNTER_SINGLE_USER` 设成 `0`**：云实例一创建就在公网上，单用户模式等于
   任何人 `POST /api/auth/local-session` 都能拿到 admin token。向导第 5 步会引导建管理员。
3. **K8s / Sealos 记得 `fsGroup: 1001`**（R0 第四节）。向导第 1 步的「卷可写」会把这个问题
   当场报出来，模板调好之前先拿它验一遍。
4. 向导的来源判断依赖 web BFF 注入的 `X-Hunter-Forwarded-For`。**平台自带的反代如果不写
   `X-Real-IP` / `X-Forwarded-For`，来源会判成 unknown（按公网处理，要求口令）** ——
   这是安全的那一边，但模板文档里要写清楚。
5. `data/llm-presets.json` 随 api 镜像走。换预设 = 重建 api 镜像；改数值必须同步
   `docs/model-testing/model-compat-matrix.md`（那是唯一的数据来源）。
6. 截图可复现：`scripts/setup-wizard/mock-gateway.py` 起一个本机模拟网关，
   向导指向它就能拍出不含任何真实地址的截图。
