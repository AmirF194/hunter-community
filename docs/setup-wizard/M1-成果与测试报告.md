## 二、偏离设计方案的决策与原因

| # | 方案原写法 | 实际做法 | 原因 |
|---|---|---|---|
| 1 | 热生效用 `PATCH /config` | **`PATCH /global/config`** | R0 实测：`PATCH /config` 写的 `<实例目录>/config.json` 根本不在 opencode 的配置加载路径上，返回 200 但永不生效。详见 R0 第一节 |
| 2 | `gen-config` 写一份配置 | **分两处写**：`mcp`/`instructions` → 项目 `opencode.json`；`provider`/`model` 来源为 env 时写项目文件、来源为数据库时写全局 `opencode.jsonc` | 项目文件优先级高于全局，而热生效只改全局。这样「环境变量锁定」是靠优先级天然实现的，向导改不动 |
| 3 | SKILL 同步写 huntercode 插件 `hunter-skill-sync.ts`，发 `hc-v1.18.12-slim.2` | **不写插件、不发新基础镜像**，用 opencode 原生 `skills.urls` | R0 实测原生能力已完整覆盖（0.07 秒可见、模型真能调用），插件钩子里也没有 HTTP 路由扩展能力。少一个 fork 改动就少一处漂移 |
| 4 | 新表 `user_skill_files`，数据库为准 | **不建这张表**，文件系统（api 自己的卷）为准 | 3.5 要解决的是「opencode 看不到 api 写的 SKILL」，导出接口已经解决；再存一份到数据库就有两个事实来源，`skill_files.py` 十几个写入分支每个都要双写，漏一处就是「界面显示 A、模型看到 B」。详见 [M1-D](./M1-D-SKILL同步.md) 第四节 |
| 5 | 默认 compose「`build:` 保留但走 `image:`」 | **默认文件里一个 `build:` 都不留** | compose 同时有 `image:` 和 `build:` 时，本地没有该镜像会去**构建**而不是拉取 —— 云平台和新用户会莫名其妙开始编译 Next.js |
| 6 | api 镜像用 additional build context | **构建上下文改仓库根** | additional context 需要 Compose v2.17+/较新 BuildKit，而 1Panel、Sealos、老版 Docker Desktop 版本参差；这是「一键部署」场景，不能要求用户先升级 compose |
| 7 | 多架构用 QEMU | **原生 arm64 runner 分平台构建 + `imagetools create` 合 manifest** | web 的 Next.js 构建与 api 的 pip 编译在 QEMU 下慢一个数量级、常超时。本仓是公开仓库，`ubuntu-24.04-arm` 免费可用 |

## 三、方案之外、实测才发现的问题（都已修）

这几条不在任务书里，但不修就是线上故障。

### 3.1 `db/migrations` 里有 7 个文件一直在静默失败

`db/migrations/*.sql` 依赖的基础表（`stocks` / `klines` / `backtest_result`）不是迁移文件建的，
而是 `app/services/database.py::init_db()` 在 FastAPI lifespan 里建的。
而 compose 把 `./db/migrations` 挂成 postgres 的 `docker-entrypoint-initdb.d` —— **initdb 在 api 第一次启动之前就跑**，
那时基础表还不存在。空 postgres 只灌迁移文件的实测：

```
ERROR:  relation "stocks" does not exist            (0007 / 0015)
ERROR:  relation "klines" does not exist            (0008 六处、0010 / 0014 建视图)
ERROR:  relation "backtest_result" does not exist   (0013)
```

而 initdb 的 psql 默认不带 `ON_ERROR_STOP`，失败被静默吞掉。
→ `app/migrate.py` 改成两阶段：先 `init_db()`，再跑增量迁移；日志分两段打。

### 3.2 `0010_daily_close_view.sql` 会让**演示站**升级后起不来

0010 建 7 列的 `daily_close`，0014 用 `CREATE OR REPLACE VIEW` 加到 8 列（`adv_20d`），
而 OR REPLACE **不许减列**。中招的是「手工补跑过迁移、但 `schema_migrations` 账本是空的」那类库 ——
账本空 ⇒ 执行器从 0001 重跑 ⇒ 撞上 0010。

**fin-r1 演示站正是这种库**（实测：`schema_migrations` 不存在、`daily_close` 已是 9 列）。

反证实测（干净 postgres，先跑 0014 建出 9 列视图，再重跑 0010）：

| | 结果 |
|---|---|
| 修复前的 0010 | `ERROR: cannot drop columns from view` · 退出码 **3** |
| 修复后的 0010 | `DROP VIEW` / `CREATE VIEW` · 退出码 **0** |

→ 给 0010 开头加 `DROP VIEW IF EXISTS daily_close;`。
**现在改代价为零**：`schema_migrations` 是本版本才引入的，世上还没有任何库记录过它的 checksum；
过了这个版本再改，所有已部署的库启动时都会刷「迁移文件被改过」的 WARNING。
**不带 `CASCADE`**：已 grep 确认只有 Python 查询引用该视图，将来真有 SQL 依赖时应该大声失败而不是静默连带删除。
CI 的「逐个文件重跑」白名单相应清空（留白名单等于让这一步看不见这个回归）。

### 3.3 api 同步调 opencode 会死锁（子任务 D 在端到端验证中撞到）

改成 URL 拉取后 `api → opencode /skill/refresh` 变成闭环（opencode 会回头 GET api 的清单）。
`opencode_admin.refresh_skills()` 是同步 httpx，从 `async def` 里调会堵死 uvicorn 单 worker 的事件循环：

```
17:08:27.498 WARNING [opencode_admin] refresh 请求失败: timed out     ← 等满 30 秒
17:08:27.502 INFO    [internal.skills] 导出清单 · 2 个用户 SKILL      ← 阻塞一放弃，立刻就服务了
```

表现是「保存 SKILL 要 30 秒然后提示请重启 opencode」，而文件其实早写好了、opencode 也活着。
→ `chat_skill._after_write()` 改 async + `run_in_threadpool`，**30.07 秒 → 0.164 秒**。
`apply_llm()` 的 docstring 里也写明了同一个闭环（M2 的就绪探测必须同样处理）。

### 3.4 8 + 10 处硬编码把开源用户的数据发给我们自己的网关

10 个读 `LLM_*` 的文件里有 **8 处**把 `LLM_BASE_URL` 的默认值写成了我们演示站的网关地址；
`ONE_API_BASE_URL` 另有 **10 处**同样问题（attribution / signal_monitor ×2 / thesis_gen /
research_assistant ×2 / gm 的 guardian·research·assistant·recap）外加一个调试脚本。

开源用户没配地址时，他的数据会被发到我们服务器上。
→ 前 8 处直接删（未配置就是未配置）；后 10 处新增 `runtime_config.one_api_base_url()`：
`ONE_API_BASE_URL` 非空时优先不变，否则回落到这个部署自己配的大模型地址。
**只修一半反而更糟** —— 同一个部署里一部分功能老实报「未配置」、另一部分照样往我们这儿发。

### 3.5 升级会让老用户装过的 SKILL 从界面消失

`./user-skills` 与 `./data-packages` 从 bind mount 改成具名卷之后，**新卷是空的**。
文件一个都没丢（还在部署目录里），但容器看不到 —— 症状看起来像「升级把我的东西弄丢了」。
演示站有 **18 个**用户 SKILL。
→ `scripts/migrate-volumes.sh`（幂等、带 `--dry-run`）+ `boot.sh` 在空卷时打提示 + README 升级小节。

### 3.6 构建上下文改到仓库根之后，真实部署目录构建不出来

演示站第一次构建当场失败：

```
checking context: no permission to read from
  '/home/support/hunter-community/data-packages/hunter-data-hs300-20260826.tar'
```

部署目录里的运行时数据也进了构建上下文，而那些文件是容器以 root 写的。
**干净的 clone 里这两个目录是空的，所以本机全绿、演示站第一步就挂。**
→ 根 `.dockerignore` 排除 `data-packages` / `user-skills` / `*.bak` / `.env.bak*`。

### 3.7 compose 的兜底值会让新机制永远不生效

`HUNTER_INTERNAL_KEY: ${HUNTER_INTERNAL_KEY:-hunter-internal-local}` 三处、
`LLM_DEFAULT_MODEL: ${LLM_DEFAULT_MODEL:-gpt-4o-mini}` 两处。
compose 的 `${X:-默认}` 让变量**永远非空**，而 boot.sh / runtime_config 的优先级是
「环境变量非空 → 密钥卷 / 数据库」—— 有兜底值的话第一条永远命中，
自动生成的密钥和向导写进数据库的模型名一辈子用不上。
`hunter-internal-local` 还是写在公开仓库里的公开字符串。
→ 五处全部改成 `${X:-}`。

### 3.8 web 也要同一把 `HUNTER_INTERNAL_KEY`

`apps/web/app/api/opencode/[...path]/route.ts:23` 的 BFF 调 api 的 `/api/internal/ocr/extract`。
api 自动生成随机 key 之后 web 还拿着空值 → OCR 一律 401，而症状只是「上传图片没反应」。
→ 新增 `apps/web/entrypoint.sh` 从 `hunter_secrets` 卷读（环境变量非空优先），compose 给 web 挂上该卷只读。
`secrets.env` 定为 **1001:1001 / 640**：api 是 root、opencode 与 web 都是 uid 1001。

## 七、给 M2 的交接

1. **热生效用 `PATCH /global/config`**，服务函数 `opencode_admin.apply_llm(cfg)` 已就绪，返回 `{"ok", "reason"}`、永不抛异常。**调用时必须 `await run_in_threadpool(apply_llm, cfg)`**。
2. **就绪探测**同样不能在事件循环里同步等 —— `GET /config/providers` 会触发实例重建，重建时 SKILL 发现会回头拉 api，同步调用就是死锁。
3. **就绪判定用「当前 `model` 等于新模型」**，不要用「`models` 列表只有一个」：`updateGlobal` 是 `mergeDeep`，旧模型名会累积（容器重启时 `gen-config` 整份重写才清掉）。
4. `runtime_config.save_llm(cfg, tested_token=None)` 的 `tested_token` 参数已留出，**M1 没有实现校验**，M2 补 HMAC。
5. `runtime_config.source(key)` 支持单项判断，向导「已锁定」的展示直接用它。
6. SKILL 导出接口契约见 [M1-D](./M1-D-SKILL同步.md) 第三节，M2 装 SKILL 后照旧调 `refresh_skills()` 即可。
7. 向导第 1 步「环境自检」建议把这几项列进去：密钥来源与强度、迁移账本最新文件名、api↔opencode 双向连通、卷可写性。
8. **向导前端不要代理 opencode 的 `/config`**（明文回显 apiKey）。
