## 零、一句话结论

三个平台的模板都写完了、都过了能做的静态校验、都用「等价 compose」在预发环境
**从空卷完整跑通**（六服务健康 → 走完向导 → 真实对话 → 深度分析 → 重启数据不丢）。

**但三个平台一个都没有账号**，所以**没有任何一次真实平台部署**，也**没有上架**。
README 本轮不加部署按钮。需要用户来做的事列在第八节。

过程中实测挖出并修掉了**三个会让云用户踩坑的运行时问题**，其中一个是「向导全绿
但发消息永远没回复、日志里一条报错都没有」——这一条如果不做等价验证，会一路带到上架。

## 三、与设计方案 5.4 草图的差异（及原因）

| # | 草图 | 实现 | 原因 |
|---|---|---|---|
| 1 | `template: PREBUILT` | `PREBUILT_V2` | 官方清单要求；schema 里 `PREBUILT` 只是它的别名 |
| 2 | `DATABASE_URL` 里写死 `@postgres:5432` | `@${POSTGRES_HOST}:${POSTGRES_PORT}` | Zeabur 的主机名不是服务名。官方 troubleshooting 把「使用固定主機名稱」列为常见错误 |
| 3 | 三把密钥都写 `<模板生成的随机值>` 放在 api 上 | **借位到四个不同的服务** | `${PASSWORD}` 每服务一个，同一个服务里引用两次拿不到两个值 |
| 4 | 没有 `portForwarding` | 五个内部服务全部 `enabled: false` | 不加的话 TCP 端口会生成公网转发链接，等于把数据库暴露出去 |
| 5 | 没有卷属主处理 | opencode 加 `init` 规则 chown 1001 | 官方指南：*Zeabur Volume defaults to empty directory*。R0 已实测「空目录 + 属主不对 = 入口脚本退出」 |
| 6 | api 没有 `LLM_SHIM_URL` | **补上** | 见第四节 · 问题 3 |
| 7 | 没有 `healthCheck` / `resourceRequirement` / `instructions` / `localization` | 都加了 | schema 里有；`instructions` 用来把初始化口令显示给用户 |

Sealos 与 1Panel 的差异表分别在 `docs/deploy/sealos.md` 第七节与
`M3-E-1Panel应用包.md` 第四节。

## 四、实测挖出来的三个问题（都已修）

这三个**都不是模板写错**，是「本地 compose 能跑掩盖住的运行时问题」，
只有真的把模板跑起来才会暴露。

### 问题 1 · 云部署下 boot.sh 误报「密钥重启后会变」

**症状**：Zeabur 等价栈从空卷启动，api 日志打出

```
[boot] WARN  /opt/hunter-secrets 在容器可写层上,没有挂 hunter_secrets 卷。
[boot] WARN    密钥只活到下次 recreate;之后已保存的 key 会全部解不开、登录全部失效。
```

而同一条日志的上一行写着 `JWT_SECRET 来源=环境变量`。

**为什么是错的**：云平台不支持跨服务共享卷，模板改成由平台生成随机值、注入成
环境变量给三个服务。这时 `/opt/hunter-secrets` 落在可写层上是**正常且无害**的 ——
下次重启平台还会注入同样的值。那句「已保存的 key 会全部解不开」一个字都不成立，
云用户看到只会白白吓一跳、或者去找一个根本不存在的卷。

**修法**（`apps/api/boot.sh`）：两把密钥**都**来自环境变量时降级为 INFO 并说明原因；
其余情况告警照旧，并补一句「或（云平台上）由模板注入成环境变量」。

**验证**（把新 boot.sh 挂进 rc2 镜像的同名路径跑）：

| 场景 | 结果 |
|---|---|
| 两把都来自环境变量 | `[boot] INFO … 但两把密钥都来自环境变量 —— 重启后值不变,不影响已保存的 key。` ✅ |
| 两把都留空（真的会变） | `[boot] WARN … 密钥只活到下次 recreate` ✅ 仍然告警 |

### 问题 2 · 向导第 1 步把环境变量来的密钥报成「首启自动生成（hunter_secrets 卷）」

**症状**：Zeabur 等价栈整个栈里连 `hunter_secrets` 卷都没有，向导环境自检却显示

```
secret:JWT_SECRET : 32 个字符 · 来源：首启自动生成（hunter_secrets 卷）
```

**根因**：`setup_probe._secret_source` 靠「密钥卷文件里有没有同一个值」判断来源，
而 `boot.sh` 的 `_persist_secrets` 会把**环境变量来的值也写回文件**
（那是有意的，为了用户以后从 `.env` 里删掉也不丢）。所以这个比对**恒为 volume**。
本地部署在 `.env` 里显式设了 `JWT_SECRET` 时同样报错。

**修法**：`boot.sh` 把它自己知道的来源导出成 `HUNTER_SECRET_SRC_<名字>`
（`env` / `volume` / `generated`），`_secret_source` 优先读它；老镜像没有这个变量时
退回旧逻辑（结论不比现在更差）。文案也加了 `generated` 一档。

**验证**：同一套挂载法跑，`env-check` 输出变成
`来源：环境变量（.env 或云平台模板注入）` ✅

### 问题 3 · api 不设 `LLM_SHIM_URL` → 向导全绿但永远收不到回复 ⚠️ 最严重

**症状**：Sealos 等价栈上，向导五步全绿、`engine-ready` 返回 `true`、
`apply` 返回 `ok: true`，**发消息之后永远没有回复**。
opencode 日志里 `[hunter-auth] chat.message · verified`，assistant 消息
`parts: []`、`error: None`，llm-shim 一条请求日志都没有，**没有任何报错**。

**根因**：向导保存后 api 走 `PATCH /global/config` 把 provider 的 `baseURL`
推给 opencode，那个值取自 **api 容器的** `LLM_SHIM_URL`
（`services/opencode_admin.py:36`），不设就回落到硬编码的
`http://llm-shim:3999/v1`。而 Sealos 上 shim 叫 `<应用名>-llm-shim`、
1Panel 上叫 `<容器前缀>-llm-shim`、Zeabur 私有网络是 `llm-shim.zeabur.internal`。

实测拿到的证据：

```
provider hunter-llm baseURL = http://llm-shim:3999/v1     ← 推进去的
容器实际主机名                = huntercode-4t3jNdM6-llm-shim
```

**为什么本地 compose 看不出来**：默认 compose 里服务就叫 `llm-shim`，
回落值恰好是对的。

**修法**：三个模板的 api 服务全部补 `LLM_SHIM_URL`；根目录 `docker-compose.yml`
也显式写上（值与回落值相同，纯粹是为了让「api 依赖 shim 地址」这件事在默认文件
里就看得见）。

**验证**：补上后重新 `apply`，`baseURL` 变成
`http://huntercode-4t3jNdM6-llm-shim:3999/v1`，对话 6.6 秒拿到回复、
深度分析 53.9 秒出报告。

**遗留**：`engine-ready` 探测只问 opencode「当前生效的模型是不是刚推的那个」，
**不检查 baseURL 连不连得上**，所以这个失败在向导里是绿的。
建议 M4 给 `/setup/engine-ready` 或第 5 步补一次真实的端到端探活。

### 用例 1 · 三个模板各自的等价 compose 从空卷启动

| 平台 | 宿主端口 | 从空卷到 6 服务健康 | 密钥怎么来的 | 手工改过文件吗 |
|---|---|---|---|---|
| Zeabur | 3210 | **16 秒**（镜像已在本地） | 四把 `${PASSWORD}`，每服务一把，借位到 postgres / redis / llm-shim / api | 否 |
| Sealos | 3211 | 约 40 秒 | `${{ random(48) }}` ×2 + `${{ random(16) }}`，`defaults` 里各自求值 | 否 |
| 1Panel | 3213 | 约 35 秒 | 表单 `type: password` + `random: true` ×2 | 否 |

三个平台的 `docker compose ps` 都是六个服务 `running / healthy`
（Zeabur 与 Sealos 另有一个 `exited` 的一次性 init 服务，那是模板里 `init` 规则 /
`fsGroup` 的翻译产物，按设计就该退出）。

**关键旁证 —— 密钥确实是「一把管三家」**（`state.sh` 比对 api 与 opencode 进程
环境里的哈希，不打印值）：

```
JWT_SECRET           api=c9630f72b0ec  opencode=c9630f72b0ec  一致 ✅
HUNTER_INTERNAL_KEY  api=1fe936ed7afd  opencode=1fe936ed7afd  一致 ✅
```

**关键旁证 —— 空 PVC + fsGroup 那条真的被测到了**（Sealos）：

```
[init] 全新 PVC：已清空
drwxrwxr-x 2 root 1001 4096 .            ← 卷里只有 . 和 ..，属主 root:1001
# opencode 起来之后
uid=1001(hunter) gid=1001(hunter)
drwxrwxr-x 4 root hunter /home/hunter/.local
drwxr-xr-x 3 hunter hunter share    ← 容器自己建出来的
drwxr-xr-x 3 hunter hunter state
```

1Panel 这条是**反证**：`scripts/init.sh` 因为我不是 root 没 chown 成功，
opencode 当场按设计报错退出 ——

```
[boot] ❌ 会话数据目录 /home/hunter/.local 不可写(当前属主 1000:1003,容器以 uid 1001 运行)。
```

用 root 容器补 chown 之后，六个服务立刻全部 healthy。**说明这条要求是真实存在的，
不是保险起见加的。**
