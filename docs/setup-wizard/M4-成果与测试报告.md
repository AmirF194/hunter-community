## 三、实测挖出来的九个问题（全部已修并复验）

前四个是等价验证挖出来的（云部署专属），后五个是全面回归挖出来的（影响所有人）。

### 问题 1 · Railway 的卷带 `lost+found`，直接当 PGDATA 用 postgres 无限重启

**症状**（Railway 等价栈）：

```
initdb: error: directory "/var/lib/postgresql/data" exists but is not empty
initdb: detail: It contains a dot-prefixed/invisible file, perhaps due to it being a mount point.
initdb: hint: Using a mount point directly as the data directory is not recommended.
```

**原因**：Railway 的卷是 ext4 块设备，文件系统根目录天生带一个 `lost+found`，
于是挂载点**永远不是空的**，而 `initdb` 拒绝在非空目录上建库。

**为什么本机试不出来**：Docker 具名卷没有 `lost+found`。我是先在等价栈里写了一个
「首次挂载时清空卷」的 init 服务（为了模拟 Railway 的卷不拷贝镜像内容），
它留下的 marker 文件**碰巧**复现了这个失败 —— 顺着查下去才发现这是 Railway 上
广为人知的一个坑。

**修**：清单里给 postgres 加 `PGDATA=/var/lib/postgresql/data/pgdata`（卷仍挂原路径）。
翻译器也改成在清空后**主动造一个 `lost+found`**，让这个必炸的配置在本机就能炸出来。

### 问题 2 · api 的卷原本挂在 `/opt/hunter-data`，会把镜像自带的静态数据整个遮掉

Railway **一个服务只能挂一个卷**（官方限制），而 api 要两份可写数据，所以合并成
一个卷的两个子目录。第一版把挂载点选在了 `/opt/hunter-data` ——
而 api 镜像的 Dockerfile 里有 `COPY data /opt/hunter-data`，那里放的是随镜像分发的
`llm-presets.json`（向导第 2 步的全部预设）、`hk_master.csv`、`recommended-skills.json`。

**这个错误在本机完全看不出来**：Docker 的空具名卷首次挂载会把镜像里该路径的内容
拷进卷，三个文件都还在（实测确实都在）。而 Railway 的卷和 K8s 的 PVC 一样**不拷贝**，
挂上去就是个空目录 —— 平台上的表现是「向导第 2 步一个预设都没有」。

**修**：挂载点改成 `/opt/hunter-vol`；翻译器加了「首次挂载时把卷清空」的 init 服务，
以后任何「把卷挂到镜像里本来有东西的路径上」的错误在本机就会暴露。
另外 api 的 `boot.sh` 启动时 `mkdir -p` 两个子目录（空卷里它们并不存在，
不建的话向导第 1 步会把两项都报成红色的「目录不存在」）。

### 问题 3 · api 绑 `::` 之后**只收 IPv6**，同网段的 IPv4 一律 Connection refused

Railway 老环境的私有网络是 IPv6-only，官方给的办法就是把服务改绑 `::`。
本轮为此加了 `HUNTER_BIND_HOST`（默认 `0.0.0.0` 不变）。在等价栈上把四家都设成
`::` 之后：

```
容器内 127.0.0.1:8000  → curl: (7) Failed to connect         ← IPv4 不通
容器内 [::1]:8000      → 200                                  ← IPv6 通
跨容器 web → api:8000  → wget: can't connect (172.22.0.6): Connection refused
```

api 因此**一直是 unhealthy**（健康检查打的是 `127.0.0.1`），而 api 自己的日志一切正常。

**原因**：asyncio 在 `create_server` 里对 `AF_INET6` **显式** `setsockopt(IPV6_V6ONLY, True)`，
内核的 `net.ipv6.bindv6only=0`（实测容器内确实是 0）在这里不起作用。
另外三家没这个问题：llm-shim 是裸 `http.server`（本轮给它加了显式的 `IPV6_V6ONLY=0`），
opencode 与 web 是 Bun / Node，默认就是双栈。

**修**：新增 `apps/api/bind.py` —— 自己建 socket、关掉 `IPV6_V6ONLY`、
再用 `uvicorn --fd` 把它交出去。修完实测：

```
[boot] 监听 :::8000（family=AF_INET6，fd=3）
容器内 127.0.0.1 → 200   ·   [::1] → 200
跨容器 web→api 200   ·   opencode→api 200
```

### 问题 4 · 重新部署之后，向导里配好的模型又变回「尚未配置」

opencode 启动时会向 api 要当前生效的大模型配置，原来是**重试 3 次、总共等 3 秒**
（注释里写的前提是「compose 的 `depends_on: service_healthy` 保证 api 已经健康」）。

**云平台大多不编排启动顺序** —— Railway 官方就是六个服务同时起，而 api 要先跑完
数据库迁移才开始监听（本轮实测 3.4～7.0 秒，老库上更久）。所以那 3 秒必然打空：

```
[gen-config] 第 1/3 次拉配置失败(URLError: Connection refused)
[gen-config] 第 2/3 次拉配置失败(URLError: Connection refused)
[gen-config] 第 3/3 次拉配置失败(URLError: Connection refused)
[gen-config] 配置来源:尚未配置
```

opencode 于是带着占位 provider 起来。**用户在向导里配好的模型，每次重新部署之后
都失效**，而日志里只有这三行连接被拒 —— 没有任何一句说「你的配置丢了」。

**修**：改成按预算退避重试（`HUNTER_CONFIG_WAIT`，默认 90 秒），
**且只对「连不上」重试** —— api 一旦回话（哪怕回的是 `configured=false`）立刻按它说的办，
全新安装一秒都不多等。修完实测：

```
[gen-config] 第 1 次拉配置失败,1 秒后重试(还剩 90 秒预算)(Connection refused)
[gen-config] 第 2 次拉配置失败,2 秒后重试(还剩 89 秒预算)(Connection refused)
[gen-config] 第 3 次拉配置失败,3 秒后重试(还剩 87 秒预算)(Connection refused)
[gen-config] api 第 4 次尝试时回话了
```

### 问题 5 · 合规声明弹窗盖住首启向导，「下一步」点不动

全新安装的用户打开首页 → 自动跳 `/setup` → **一张 `fixed inset-0 z-50` 的全屏
合规声明遮罩盖在向导上并拦截所有点击**。playwright 30 秒内重试 60 多次全部被
`intercepts pointer events` 拦掉；真人要先勾选再点「确认继续」才能继续。

弹窗本来就写了 `/setup` 不弹 —— 但**路径是在组件挂载时判的**。全新用户落在 `/`，
由首页在客户端 `replace` 到 `/setup`，而弹窗的判定回调延迟 2.5 秒才跑完，
那时人已经在向导里了。

**修**：落地时再判一次路径。**开箱第一屏应该是向导，不是合规弹窗。**

### 问题 6 · 向导第 4 步「免费开源数据源」承诺了它做不到的事

卡片写着「不用填任何东西 / A 股行情、K 线、财务走 AKShare / 腾讯等公开源，**装好就能用**」。
读代码：`choice === 'free'` 只是一个 `useState` 局部变量，**onNext 不做任何保存**。
而后端 `DATA_SOURCE_PROVIDER` 留空时默认走 hunter 网关 —— 那是**有意的**
（仓库里的注释写得很清楚：宁可如实报 `hunter_key_required`，也不悄悄回落到
容器里经常连不通的 AKShare）。

两边合起来：用户选了「免费开源数据源」，第一条对话就顶出一张红色的
「无法拉取 行情 · `hunter_key_required`」。

**修**：后端那个取舍是对的，**问题在文案**。改成如实说明：
现在能用的（K 线 / 财务 / 新闻 / 研报 / 龙虎榜 / 十大股东 / 治理，深度分析跑得完）、
现在不能用的（实时行情会明确提示未配置，**不会编一个价格给你**）、以及两条补齐的路。

### 问题 7 · 向导第 1 步把首次生成的密钥说成「还没落进 hunter_secrets 卷」

其实 `boot.sh` 生成之后紧接着就写回卷了（写不进去时它会单独告警）。
实测 `/opt/hunter-secrets/secrets.env` 早就写好了（140 B、属主 1001、权限 640）。
**修**：只陈述事实 ——「本次启动首次生成」。

### 问题 8 · 冷启后头几十秒，向导第 1 步必现一条黄色 `ReadTimeout`

「opencode → api 反向连通」这一项不是 ping，是让 opencode 现扫一遍 SKILL 目录再返回。
刚启动那几十秒它还在加载 6 个插件、连 MCP，3 秒的探测超时必然打空
（热起来之后实测只要 **16～80 毫秒**）。而向导第 1 步恰恰是用户开机后看的第一屏，
在那里甩一句 `ReadTimeout: timed out` 纯属吓人。

**修**：这一项的超时单独放宽到 10 秒；超时时的文案从裸异常改成
「对话引擎还在启动（等它 10 秒没扫完 SKILL）」+「等半分钟点一次『重新检查』」。

### 问题 9 · 老用户升级时，README 让跑的那个脚本给的指引本身是错的

两处，都是升级路径上的实测（见第四节路径 1）：

1. **`docker compose -p <名>` 起的栈，脚本认不出项目名** —— `-p` 只活在那一条命令里、
   不落任何文件，脚本问 `docker compose config` 拿到的是 compose 文件里写的
   `hunter-community`，于是报「卷 `hunter-community_hunter_user_skills` 还不存在，
   先 up -d 建出来」。失败模式是安全的（不会搬错地方），但把人往完全错误的方向带。
   **修**：支持 `--project` 与 `COMPOSE_PROJECT_NAME`；卷找不到时**把机器上同名后缀的
   卷列出来**，直接告诉用户项目名应该填什么。
2. **脚本末尾提示的那条 refresh 命令是 401** —— 它直接 `curl` opencode 的
   `/skill/refresh`，而开了 `OPENCODE_PASS` 的部署需要 basic auth；更糟的是
   `curl -s` 把 401 的响应体也吞了，**看上去像是成功了**。
   **修**：改成 `docker compose restart api opencode` —— opencode 重启时会自己
   按 `skills.urls` 重新拉一遍，不需要任何凭据。

## 九、给后续的交接

1. **等价验证这套方法已经跑通五个平台了，继续用。** 加平台只要在
   `template-to-compose.py` 里加一个 `translate_<平台>`，其余（wizard.sh / chat.py /
   state.sh）一行都不用改。
2. **加平台时先问「这个平台的卷是什么语义」。** 本轮最值钱的两个发现
   （`lost+found`、卷不拷贝镜像内容）都来自这一条。Docker 具名卷的语义是**最宽松的**，
   拿它当基准一定会漏。
3. **`validate-templates.py` 每抓到一个真问题就往里加一条规则。** 它现在 58 项，
   其中 31 项是这一轮新加的，全都是真踩到过的。
4. **发布前先把四条用户路径跑一遍。** 本轮九个问题里有五个是回归挖出来的，
   而不是写新代码时想到的 —— 其中两个（合规弹窗、第 4 步文案）影响的是
   **每一个新用户看到的第一屏**。
5. **拿到平台账号之后**：按各篇文档的「待核实」清单逐条核，核完删掉文档开头
   那句「没有在真实平台上跑过」，再往 README 加按钮。**按钮和实测是一件事，
   不要分开做。**
